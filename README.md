# 買取相場チェックツール（MarketPrice Assistant）

貴金属・アクセサリーを購入する際に、**「その価格で買っていいのか」を相場から判断する**Windowsデスクトップアプリケーションです。

Web上から貴金属相場を自動取得して表示し、商品価格と相場の差額から判定を出します。

---

## 作った背景

前職では買取専門店で、貴金属・アクセサリーの出張買取を2年半担当していました。

この仕事で身についたのが、**値段を見たらまず相場と突き合わせる**という癖です。ところがいざ自分が個人で買う側に回ると、その確認が意外と面倒でした。**相場の情報源が分散していて、そのたびに複数のページを開いて回る必要がある**からです。

**「相場を自動で集めて、手元の価格と並べて出せば、その場で判断できるのでは」** と考えたことが、このツールを作ったきっかけです。

なお判定の構造そのものは、用途を変えても成立すると考えています。詳しくは後述の「判定ロジック」に書きました。

---

## 現在の実装状況

本アプリは2つの機能で構成されています。

| # | 機能 | 状態 |
|---|---|---|
| 1 | 貴金属相場（K18 / Pt850）の自動取得・画面表示 | 実装済み |
| 2 | 商品価格と相場の差額による判定 | **ダミーデータで検証中** |

**現時点では1と2が連携していません。** 判定部分は固定値を使い、ロジックの妥当性を検証している段階です。取得した相場を判定へ流し込む実装が、次の最優先タスクです。

## 判定ロジック

商品価格から相場を引いた額（`OverPayment` ＝ 相場より余分に払う額）で、4段階に判定しています。

| 相場との差 | 判定 |
|---|---|
| **相場より安い**（マイナス） | 超買い |
| 0 〜 3,000円 高い | 買い |
| 3,000 〜 5,000円 高い | 見送り |
| 5,000円以上 高い | きつい |

### このしきい値の根拠

**現在の数値は、自分の毎月の可処分所得を基準にしています。**

相場との差額は、そのまま自分の財布から余計に出ていく額です。**3,000円までなら月のちょっとした出費を1回削れば吸収できる。5,000円を超えると生活のやりくりに影響が出始める。** その体感をそのまま境界にしました。

### 「超買い」を分けた理由

当初は3段階でしたが、**「相場より安い」と「少し高いが許容範囲」は意味が違う**と考え、分けています。

前者は買う理由そのものですが、後者は「払える」というだけです。同じ「買い」でまとめると、この差が消えてしまいます。

### この基準は、用途によって変わります

**しきい値の意味は「誰がこの判定を使うか」で変わります。**

| 用途 | しきい値の根拠になるもの |
|---|---|
| 個人の購入判断（現在の実装） | 自分の可処分所得から無理なく出せる額 |
| 仕入れ判断（転売を前提とする場合） | 手数料・送料を差し引いて確保したい利幅 |

**判定の構造（相場との差額をしきい値で区切る）は共通で、変わるのは数値の根拠だけです。**

つまり**この数値はコードに埋め込むべきものではありません。** 後述の「今後の改善点」で設定ファイル化を上位に置いているのは、この理由によります。

## 実装で意識したこと

### 1. 取得先サイトへ繰り返しアクセスしない

取得したHTMLをローカルにキャッシュし、**2回目以降はキャッシュから読む**構成にしています。

動作確認のたびに実行するツールなので、素直に書くと起動のたびに相手のサーバーへリクエストが飛びます。開発中に何十回も叩くことになるため、**先方に不要な負荷をかけない**ことを優先しました。

### 2. 相場が取得できなくても落ちないようにする

開発中、対象ページの構造が想定と違い、`NullReferenceException` でアプリが停止しました。

原因を特定したうえで、**取得結果が null の場合は代替文字列を返す**処理を追加しています。この判定は金・プラチナの両方で必要になるため、**共通メソッドに切り出して重複を排除**しました。

外部サイトに依存する以上、取得できない状況は必ず起こります。**その時にアプリごと落とさない**ことを優先しています。

### 3. 画面と処理を分離する

MVVMパターンに沿って、画面（View）とデータ・処理（Model / ViewModel）を分けています。判定条件や取得処理を画面のコードに直接書くと、条件を変えたいときに画面ごと触ることになるためです。

### 4. 変数名に計算の向きを持たせた

当初、差額を `Difference`（差額）という名前で保持していました。**この名前では「価格から相場を引いたのか、相場から価格を引いたのか」が分かりません。**

実際に、自分が想定していた計算の向きとコードの向きが逆になっており、判定結果が合わないところで初めて気づきました。

そこで **`OverPayment`（相場より余分に払う額）** に変更しています。名前を見れば向きが分かるため、読み返したときに解釈を迷わなくなりました。

## 今後の改善点

現時点で認識している課題を、優先度順に並べています。

### 1. 取得した相場が判定ロジックに接続されていない

現在は画面表示と判定が独立しており、実運用では使えません。素材（K18 / Pt850）と商品を紐づける仕組みが必要です。

### 2. 判定のしきい値がコードに直書きされている

3,000円／5,000円をコード内に埋め込んでいます。前述のとおり、**この数値は用途によって変わるべきものです。** 設定ファイルから読み込む形にして、使う人が自分の基準を設定できるようにしたいと考えています。

### 3. 初回起動時に相場が画面へ反映されない

相場を保持する `MarketPrice` クラスに変更通知（`INotifyPropertyChanged`）を実装していないため、キャッシュがない状態での非同期取得では画面が更新されないはずです。

現在動作しているのは、キャッシュファイルが存在する場合に取得処理が同期的に完了し、画面へのバインディングが評価される前に値が入るためです。**動いてはいますが、成立条件に依存した状態です。**

### 4. 導入したMVVMライブラリの機能を使えていない

`CommunityToolkit.Mvvm` を導入し `ObservableObject` を継承していますが、**`[ObservableProperty]` や `SetProperty()` といった機能を一度も使っていません。** 現状では参照しているだけで、実質的に効果がない状態です。

上記3の変更通知は、このライブラリを正しく使えば解決できます。**まず何のために入れたライブラリなのかを理解したうえで、3とあわせて対応する**のが次の課題だと考えています。

### 5. 取得先のHTML構造が変わると動かなくなる

XPathで直接ノードを指定しているため、ページ構成の変更に弱い構造です。取得部分を差し替えやすい形に切り出したいと考えています。

## 補足

- 相場情報の取得は、対象サイトの利用規約を確認したうえで、**個人利用の範囲**で実行しています。
- 取得したHTMLのキャッシュはビルド出力先に生成され、リポジトリには含めていません。
- 判定の基準値は実務の査定基準とは一切関係のない、自分で設定した値です。
